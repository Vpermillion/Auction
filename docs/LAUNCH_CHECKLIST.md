# Before any real-money launch

This is a synthetic, local/controlled-preview implementation. Completing software checks alone does not authorize a real-money business.

- Obtain Mongolian legal review for the auction model, seller agreement, buyer eligibility and bids, consumer remedies, cancellations, disputes, platform responsibilities, privacy/data retention, required disclosures, tax and invoicing. These are questions for counsel, not conclusions about current law.
- Complete professional Mongolian translation of all seller, buyer, admin and policy text; agree precedence between language versions. Current localization covers shared labels and key bidding notices, not the entire application.
- Agree actual per-event or subscription pricing and manually invoice the seller. No settled commission or online subscription billing exists.
- Define a seller identity review process and clearly state its scope separately from seller evidence, independent item inspection and authentication. Decide which item categories/evidence are suitable. Stock photographs must be replaced by actual item photographs.
- Use synthetic data until lawful collection, retention/deletion, privacy contact, access/correction requests and incident handling are agreed. Do not collect identity documents through this implementation.
- For direct seller payment, agree precise payment instructions, reconciliation, buyer deadlines, remedies, fulfillment and nonpayment review. If adding QPay/another provider, obtain authorized arrangements/credentials, implement a provider adapter and verify payment server-side using its official documented process. Authenticate callbacks, prevent replay/duplicate credit and test failure paths. A redirect/screenshot is never proof. The shipped adapter intentionally raises errors.
- Create named private accounts; remove known demo credentials and disable their display with `DEMO_MODE=0`. Add password change/recovery, email verification, account-level authentication abuse defenses and operator MFA or equivalent restricted access. No recovery/email flow ships today.
- Deploy only after an independent security review, HTTPS, secure cookies, reliable secret injection, private operator access, a configured trusted-proxy policy, resource limits and infrastructure rate limits. Do not trust arbitrary forwarded IP headers. Single-host SQLite must use a persistent local disk, not shared/network/ephemeral storage. Load-test the intended volume; migrate the database if one writer becomes a bottleneck.
- Establish encrypted backups, restore drills, clock synchronization, health/error monitoring, event-day support, report response times, public support contact and closed-outcome correction procedures. The current reports are stored internally and send no notification. Audit records resist app-level editing, not malicious disk access.
- Arrange an external recurring `close-auctions` invocation if unattended closing records need immediate timestamps/notifications. Current request-driven closure is safe for acceptance and winner selection but no background worker or email notification runs. The displayed final deadline is authoritative even if the first closing read occurs later.
- Add secure real-item photo/document management only after defining file size/type limits, content validation, private storage, malware handling and access rules. Current upload requests are rejected; bundled demo photos are the only image options.

No live payment, production hosting, legal review, paid customer validation, shill detection guarantee or comprehensive accessibility certification is claimed.
